# MVC controllers instead of minimal APIs

Every route is an `[ApiController]` class with attribute routing rather than a `MapGet`/`MapPost` lambda. Minimal APIs were the v1 choice and worked, but the API's twenty operations repeat three concerns — the admin CSRF/auth guard, paging validation, and the documented response for each status — as builder chains that hide them from the action they belong to. Attributes declare routing, authorization, validation and response contracts on the method that has them, and the guard becomes one filter on a base class instead of a group-level `AddEndpointFilter`.

**Consequences.** OperationIds are pinned with `[EndpointName]` because `contracts/openapi.json` is committed and Orval names the generated frontend client after them: `ListCollections` must stay `ListCollections` or the SPA stops compiling. Automatic model validation reports CLR property names, so an `InvalidModelStateResponseFactory` camel-cases them back to the documented `page`/`pageSize` keys. Response content types are declared on each `[ProducesResponseType]` because MVC's default formatters would otherwise advertise `text/plain` and `text/json` alongside `application/json`. Controller names become OpenAPI tags (`Gallery`, `Health`, `AdminGallery`, `AdminSession`), which is the intended change to the published document. The upload action reads the form from the request instead of binding `IFormFileCollection`, because the generator documents a bound file collection as `application/x-www-form-urlencoded`, which that route does not accept.

**Rejected.** Staying on minimal APIs — fewer moving parts, but the shared behaviour stays in helper functions and chained builders. One endpoint filter per concern — works, but the guard already needed rewriting and attributes are what MVC controllers are for.
