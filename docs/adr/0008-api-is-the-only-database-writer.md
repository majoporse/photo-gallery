# The API is the only writer of the gallery database

`ProcessUploadHandler` and `UploadSweeper` wrote `Uploads` and `Photos` from the worker, so two deployments shared one schema: the worker depended on column layout, on `PhotoPositions`, and on a `SELECT 1 ... FOR UPDATE` protocol against `Collections` that nothing declared anywhere. The worker now only renders. It consumes `ProcessUpload`, writes derivatives to the object store, and answers with `PhotoProcessed` or `UploadRejected`; a handler in the API turns that answer into the Photo insert and the terminal status change in one transaction. `Uploads`, `Photos` and `Collections` have exactly one writer.

**Consequences.** The worker's dependency set shrinks to two ports (object store, message bus) plus `Gallery.Contracts`. It has no EF model, no migrations, no `Upload` aggregate and no connection string for anything other than the Wolverine transport: it still connects to Postgres, it just never reads or writes `public`. It therefore never has to roll in lockstep with a schema change.

The protocol carries data rather than an id to look up: `ProcessUpload` is `{UploadId, PhotoId, ObjectKey, FileName}`, which makes those fields immutable after publish. Delivery is at-least-once on both hops, so the reply handler repeats the insert-or-skip guard that used to live in the worker; a duplicate costs a no-op.

Finality splits, deliberately. The worker retries inside Wolverine and then publishes `UploadRejected` with `ProcessingFailed` and the exception text. A sweeper in the API catches what no message can report — a reply never delivered, a worker killed mid-render — by re-publishing a `Queued` upload older than a threshold, incrementing a new `Attempts` counter, and rejecting it once that count is exhausted. `Processing` is gone as a status: it only ever distinguished "not picked up" from "picked up and died", and both are answered by re-publishing. Rejections delete the bytes in the worker, which already holds the store and the proof that they are useless; if the reply is then lost, the re-published job finds nothing and records `MissingBytes` rather than the original reason, which is a wrong story with the right outcome.

The API is now a message consumer. What it accepts is one transaction per photograph, so the argument in ADR 0007 for keeping rendering out of the web host still holds: the ban was on CPU-bound encodes, not on background writes. Status fan-out still needs `LISTEN/NOTIFY`, because the reply may land on either of the two API replicas while the admin's stream is attached to the other. Derivatives orphaned by an upload that expired mid-render are acceptable: keys are content-addressed and the next attempt overwrites them.

Image rendering is no longer reachable from the API, so demo seeding cannot render inline either. `seed` creates the Upload and puts the bytes, then stops. It does not publish: a one-shot command stops its host before Wolverine's sender has flushed, and a lost publish is exactly what the sweeper repairs, so the rows are left `Uploaded` for the next sweep. A fresh environment fills up a minute after the command returns, which is the honest price of having no running bus.

`Gallery.Contracts` deliberately does not reference `Gallery.Domain`. The worker names its outcome in contract terms, and the API maps `RejectionReason` to `UploadRejection` with an explicit switch. A wire format that moved whenever the domain enum moved would make every domain refactor a protocol change.

**Rejected.** Letting the worker keep writing its own rows: fewer moving parts, but two writers on one schema and an unstatted contract in the shape of a table. A shared imaging library so the API can still render during seeding: it re-shares the exact code this decision separates, and the worker would still not be allowed to write the Photo it just made. A broker so the worker need not connect to Postgres at all: ADR 0007 priced that and declined, and nothing here changes the volume. An HTTP callback from the worker: it reaches the same single-writer result but loses the durable retry the queue provides for free. A third `UploadStarted` message so the status could be truthful: a message per upload to record something no remedy depends on.
